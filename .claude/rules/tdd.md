# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라. 그대로 따른다.**

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그쪽이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 침묵하는 부분에만 적용한다.

## 1. 적용 기준

### TDD 필수

- **비즈니스 로직**
- **API** (라우트 핸들러, 외부 API 호출 래퍼, 응답 후처리)
- **유틸리티 / 순수 함수**
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성)
- 기존 동작을 바꾸는 모든 변경

### TDD 불필요

- **타입 정의** (`type`, `interface`만 있는 파일)
- **설정 파일** (tsconfig, vite/eslint 설정, package.json 등)
- **순수 UI** (로직 없는 마크업, 스타일링, 레이아웃)
- **SQL / 스키마 정의**

경계가 모호하면 **로직이 있으면 적용**으로 판단한다.

## 2. RED - GREEN - REFACTOR

### RED

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 마라.
- 테스트 이름은 기대 동작을 서술한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 오타로 인한 실패는 RED가 아니다. 테스트를 고쳐 올바른 이유로 실패시켜라.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 지금 테스트가 요구하지 않는 기능, 옵션, 추상화를 넣지 마라.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체 실행으로 확인한다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지**한다. 변경마다 테스트를 실행한다.
- **새 동작을 추가하지 마라.** 새 동작은 다음 RED에서 한다.

### 반복

- 다음 동작이 남아 있으면 **RED로 돌아간다.** 한 사이클을 끝내기 전에 다음 기능을 시작하지 마라.

## 3. 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 다시 시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 복사해 두고 보며 다시 쓰기 모두 포함한다.
- 삭제 후에는 테스트를 먼저 쓰고, 코드는 GREEN 단계에서 새로 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| 너무 단순해서 테스트 불필요 | 단순한 코드는 테스트도 10초면 쓴다. 단순하다고 믿은 코드에서 버그가 나온다. 테스트가 이후 변경의 안전망이 된다. |
| 나중에 테스트 추가하겠다 | 나중은 오지 않는다. 사후 테스트는 구현에 맞춰 쓰게 되어 바로 통과하므로 아무것도 증명하지 못한다. |
| 시간이 없다 | 디버깅과 회귀 수정이 더 오래 걸린다. TDD는 속도를 늦추지 않고 재작업을 줄인다. |
| 삭제하면 낭비다 | 매몰 비용 오류다. 검증되지 않은 코드를 유지하는 비용이 더 크다. 다시 쓰는 건 빠르다. |
| 프로토타입이다 | 프로토타입은 운영 코드가 된다. 버릴 코드라면 테스트 없이 작성하고 반드시 폐기하라. 남길 코드라면 TDD다. |
