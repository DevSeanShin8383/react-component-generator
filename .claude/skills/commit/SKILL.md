# Commit

변경사항을 분석해 컨벤션에 맞게 커밋한다. 사용자의 별도 승인을 받지 않고 바로 커밋한다.

## 절차

### 1. 변경사항 분석

먼저 git 저장소인지 확인한다. 저장소가 아니면 중단하고 사용자에게 알린다.

```bash
git status --short
git diff            # 아직 스테이징하지 않은 변경
git diff --staged   # 이미 스테이징한 변경
git log --oneline -10   # 기존 메시지 스타일 참고
```

- 변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.
- untracked 파일은 내용을 읽어 의도를 파악한다.
- `.env`, 키·토큰이 들어간 파일, `node_modules`, `dist` 같은 빌드 산출물은 커밋 대상에서 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류

하나의 커밋은 하나의 목적만 담는다. 파일이 아니라 변경의 의도를 기준으로 나눈다.

- 기능 추가, 버그 수정, 리팩터링, 설정 변경이 섞여 있으면 각각 분리한다.
- 같은 목적의 코드와 테스트는 한 커밋에 둔다.
- 한 파일에 서로 다른 목적의 변경이 섞여 있으면 사용자에게 알리고, 필요하면 `git add -p` 대신 분리 방안을 제안한다.
- 단위가 하나뿐이면 억지로 나누지 않는다.

### 3. 커밋 메시지 작성

형식:

```
type: 요약

(필요할 때만) 변경 이유와 맥락을 본문에 작성
```

| type | 용도 |
| --- | --- |
| feat | 새 기능 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 설정, 의존성, 빌드, 기타 잡무 |

위 네 가지로 애매할 때만 `docs`, `style`, `test`, `perf`를 쓴다.

규칙:
- 요약은 한국어로, 50자 안팎의 한 줄로 쓴다. 끝에 마침표를 붙이지 않는다.
- "무엇을 했는지"보다 "무엇이 달라졌는지"가 드러나게 쓴다. 예: `feat: 결과 카드에 창 형태 타이틀바 추가`
- 본문은 요약만으로 이유가 전달되지 않을 때만 쓴다. 무엇을 바꿨는지는 diff가 이미 말해 준다.
- 최근 `git log`에 다른 스타일이 확립돼 있으면 그것을 따른다.
- 메시지 마지막에 시스템 안내로 받은 Co-Authored-By 줄을 붙인다.

### 4. 커밋 실행

승인 절차 없이 단위마다 순서대로 바로 실행한다. 사용자가 커밋을 요청한 것 자체가 승인이다.

```bash
git add <해당 단위의 파일들>
git commit -m "<메시지>"
```

- `git add -A`, `git add .`는 쓰지 않는다. 파일을 명시해서 추가한다.
- `--no-verify`로 훅을 건너뛰지 않는다. 훅이 실패하면 원인을 고치고 새 커밋을 만든다. `--amend`로 덮어쓰지 않는다.
- 모두 끝나면 `git log --oneline -N`으로 결과를 보여주고, 커밋 단위별 파일과 제외한 파일(사유 포함)을 함께 알린다.
- 잘못 커밋했다면 사용자가 `git reset --soft HEAD~N`으로 되돌릴 수 있다고 안내한다.
- 푸시는 사용자가 따로 요청할 때만 한다.
